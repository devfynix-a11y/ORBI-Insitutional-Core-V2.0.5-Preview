# ORBI API Request Contracts

This document defines the canonical request shape for registration, business
access, and gateway identity calls.

It complements the registration blueprints by showing the headers, payloads,
and method rules that clients and services must follow.

## 1. Method Rules

```text
GET
Read-only fetch. No body. Query params only when required.

POST
Create, submit, confirm, review, challenge, or perform an action. Financial,
registration, and approval actions should use POST with audit metadata and
idempotency where retries can happen.

PATCH
Partial state update. Use only when the endpoint is explicitly designed for
patching a resource.

PUT
Full resource replacement. Not used by the current registration and business
access endpoints. Do not introduce PUT for financial identity flows without a
separate contract review.
```

## 2. Public App Headers

Used by ORBI Mobile, ORBI Auth Web, and approved ORBI app surfaces.

```http
Content-Type: application/json
Accept: application/json
Authorization: Bearer <access_token>
x-orbi-app-id: <trusted_app_id>
x-orbi-app-origin: <trusted_app_origin>
x-orbi-device-id: <stable_device_id>
x-orbi-request-id: <uuid>
x-orbi-client-time: <iso_utc_timestamp>
```

`Authorization` is not required for signup and login, but is required for
profile, business, service-access, and admin endpoints.

Financial or retryable actions should also include:

```http
Idempotency-Key: <stable_operation_key>
```

Accepted aliases where implemented:

```text
Idempotency-Key
x-idempotency-key
x-orbi-idempotency-key
```

## 3. Pay Gateway Service Headers

Used by trusted third-party services calling ORBI Pay Gateway.

```http
Content-Type: application/json
Accept: application/json
Authorization: Bearer <orbi_pay_service_key>
```

Accepted service-key alternatives:

```http
x-orbi-pay-service-key: <orbi_pay_service_key>
x-api-key: <orbi_pay_service_key>
```

Retryable requests must include:

```http
Idempotency-Key: <service_stable_key>
```

The service key authenticates the external service only. It does not grant
direct Core financial authority.

## 4. Core Internal Worker Headers

Used only for Gateway-to-Core signed internal requests.

```http
Content-Type: application/json
Accept: application/json
x-worker-id: <worker_id>
x-worker-scopes: <comma_separated_scopes>
x-worker-request-id: <uuid>
x-worker-timestamp: <iso_utc_timestamp>
x-worker-nonce: <random_nonce>
x-worker-signature: <hmac_signature>
x-worker-key-id: <key_id>
```

Required scopes:

```text
gateway:identity:read
gateway:business-registration:write
```

Worker headers are generated by Gateway. Public clients and third parties must
not generate them.

## 6. Session And Profile

```http
GET /v1/auth/session
Authorization: Bearer <access_token>
x-orbi-app-id: mobile-android
x-orbi-app-origin: ORBI_MOBILE_V2026
```

```http
GET /v1/user/profile
Authorization: Bearer <access_token>
x-orbi-app-id: mobile-android
x-orbi-app-origin: ORBI_MOBILE_V2026
```

Both responses should return canonical Core identity state. Clients must not
invent missing currency, registry type, account status, or wallet identity.

## 7. Business Registration From ORBI App

```http
POST /v1/business/registrations
Authorization: Bearer <access_token>
Content-Type: application/json
Accept: application/json
x-orbi-app-id: <trusted_app_id>
x-orbi-app-origin: <trusted_app_origin>
x-orbi-request-id: <uuid>
Idempotency-Key: business-registration:<user_id>:<requested_role>
```

```json
{
  "requestedRole": "MERCHANT",
  "businessName": "Example Store",
  "phone": "+255700000000",
  "note": "Requesting merchant access for ORBI services.",
  "metadata": {
    "registration_source": "ORBI_AUTH_WEB",
    "registration_channel": "core_public",
    "consent_captured": true,
    "clientTimeContext": {}
  }
}
```

Accepted role aliases:

```text
requestedRole
requested_role
businessName
business_name
```

## 8. Business Registration Through Pay Gateway

```http
POST https://pay.orbifinancial.com/v1/business/registrations
Authorization: Bearer <orbi_pay_service_key>
Content-Type: application/json
Accept: application/json
Idempotency-Key: registration:<service_code>:<external_business_id>:merchant_application
```

```json
{
  "email": "seller@example.com",
  "phone": "+255700000000",
  "requestedRole": "MERCHANT",
  "businessName": "Example Store",
  "externalBusinessId": "shop-seller-123",
  "note": "Seller registration submitted by trusted service.",
  "metadata": {
    "registration_source": "ORBI_SHOP",
    "registration_channel": "pay_gateway",
    "source_service_code": "orbi_shop",
    "external_customer_id": "shop-customer-456",
    "consent_captured": true,
    "clientTimeContext": {},
    "riskContext": {}
  }
}
```

At least one of these must be provided:

```text
userId
email
phone
```

Gateway forwards the request to Core using signed worker headers.

## 9. Identity Resolve Through Pay Gateway

```http
POST https://pay.orbifinancial.com/v1/identity/resolve
Authorization: Bearer <orbi_pay_service_key>
Content-Type: application/json
Accept: application/json
x-orbi-request-id: <uuid>
```

```json
{
  "identifier": "OB26-9885-6029",
  "metadata": {
    "registration_source": "ORBI_SHOP",
    "registration_channel": "pay_gateway",
    "source_service_code": "orbi_shop",
    "clientTimeContext": {}
  }
}
```

`identifier` may be an ORBI customer ID, phone, or email depending on the
resolver policy. The response must be treated as identity resolution only, not
as permission to move funds.

## 10. Payment Profile Through Pay Gateway

```http
POST https://pay.orbifinancial.com/v1/payment-profiles
Authorization: Bearer <orbi_pay_service_key>
Content-Type: application/json
Accept: application/json
Idempotency-Key: payment-profile:<service_code>:<external_customer_id>
```

```json
{
  "customerId": "OB26-9885-6029",
  "externalCustomerId": "shop-customer-456",
  "scopes": [
    "payment_profile:read",
    "payments:create",
    "escrow:create",
    "balance:read"
  ],
  "consent": {
    "consent_captured": true,
    "consent_text_version": "orbi-payment-profile-v1",
    "balance_read_allowed": true,
    "expires_at": "2027-07-20T00:00:00.000Z"
  },
  "metadata": {
    "registration_source": "ORBI_SHOP",
    "registration_channel": "pay_gateway",
    "source_service_code": "orbi_shop",
    "clientTimeContext": {}
  },
  "expiresAt": "2027-07-20T00:00:00.000Z"
}
```

At least one identity field is required:

```text
userId
customerId
email
phone
```

The response returns a `paymentProfileId` such as `pp_...`. Merchants may store
that profile reference, but they must not store wallet IDs or use the profile
as automatic authority to move funds.

## 11. Service Access Requests

```http
GET /v1/service-access/requests/my
Authorization: Bearer <access_token>
x-orbi-app-id: <trusted_app_id>
x-orbi-app-origin: <trusted_app_origin>
```

```http
POST /v1/service-access/requests
Authorization: Bearer <access_token>
Content-Type: application/json
Accept: application/json
x-orbi-app-id: <trusted_app_id>
x-orbi-app-origin: <trusted_app_origin>
Idempotency-Key: service-access:<user_id>:<requested_role>
```

Payload shape is controlled by `ServiceAccessRequestCreateSchema`. The request
must identify the requested service role and provide business or agent evidence
inside structured fields or metadata.

## 12. Admin Review

```http
GET /v1/admin/service-access/requests?status=pending&limit=50
Authorization: Bearer <staff_access_token>
x-orbi-app-id: <institutional_app_id>
x-orbi-app-origin: <institutional_app_origin>
```

```http
POST /v1/admin/service-access/requests/:id/review
Authorization: Bearer <staff_access_token>
Content-Type: application/json
Accept: application/json
x-orbi-app-id: <institutional_app_id>
x-orbi-app-origin: <institutional_app_origin>
x-orbi-request-id: <uuid>
Idempotency-Key: service-access-review:<request_id>:<decision>
```

Example payload:

```json
{
  "decision": "approved",
  "note": "Business documents and owner identity reviewed.",
  "metadata": {
    "review_channel": "orbi_portal",
    "clientTimeContext": {}
  }
}
```

The current implementation uses `POST` for review actions. Do not document or
call this endpoint as `PUT` unless the API is changed.

## 13. Error Shape

Standard error response:

```json
{
  "success": false,
  "error": "VALIDATION_FAILED",
  "message": "Human readable message when available.",
  "details": []
}
```

Clients should display user-friendly text, keep the raw error in diagnostics,
and never retry financial actions without the same idempotency key.

## 14. ORBI Business Hosted Account Link

External merchant portals should not collect ORBI passwords directly. When a
seller, agent, or business user selects ORBI Pay as a settlement or payment
profile method, the portal starts an ORBI-hosted account-link flow.

Example merchant-portal start route:

```http
GET /api/auth/orbi-business/link/start?mode=login&field=bankAccount&returnTo=https%3A%2F%2Fmerchant.example.com%2Fseller%2Fregister
Accept: text/html
```

Rules:

```text
mode = login | signup
field = merchant-defined form field to receive the payment profile reference
returnTo = exact URL that should receive the final UX continuation
```

The merchant backend creates signed state, redirects to ORBI Auth, then handles
the callback:

```http
GET /api/auth/orbi-business/link/callback?code=<oidc_code>&state=<signed_state>
Accept: text/html
```

The callback exchanges the code with Keycloak/Auth, reads the ORBI identity,
creates or links a payment profile through Pay Gateway, then redirects back to
`returnTo` with sanitized query parameters.

Example returned query parameters:

```text
orbi_settlement_return=1
orbi_settlement_field=bankAccount
orbi_payment_profile_id=pp_...
orbi_payment_profile_status=active
orbi_account=OB26-9885-6029
orbi_customer_id=OB26-9885-6029
orbi_link_status=linked
```

Merchant portals may store the payment profile reference and display a masked
ORBI customer hint. They must not store Keycloak tokens, ORBI passwords, wallet
IDs, OTPs, PINs, or raw challenge evidence.

Production Auth configuration:

```text
Issuer: https://auth.orbifinancial.com/realms/orbi
OIDC discovery: https://auth.orbifinancial.com/realms/orbi/.well-known/openid-configuration
Client ID: orbi-shop-business for the reference ORBI Shop integration
Redirect URI: https://shop.orbifinancial.com/api/auth/orbi-business/link/callback
```

The `orbi-shop-business` client is confidential. Its client secret belongs in
the merchant application's server-side secret store only.
